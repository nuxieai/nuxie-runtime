# Immutable flex line source audit — L04 and L06

This is a source audit, not public admission or pixel qualification. Inspected current compiler and baseline-owned runtime/schema; `git diff 6c7ac16617835b5f581784ff08a9e779bb52faf3 --` for the three primary runtime/schema files below was empty. No runtime or compiler files changed.

## Ordinary properties actually reachable

- `crates/nuxie-schema/src/generated/schema.rs:15275`: `LayoutComponentStyle.flexWrapValue`, key 604, uint, defaults 0. `layout_style_applier.rs:216` maps 0=no-wrap, 1=wrap, 2=wrap-reverse. `layout_component_style.rs:400` reads this property and `:236` applies it. `layout_style_applier.rs:489` maps reverse to Taffy FlexWrap::WrapReverse. This is a native candidate for line formation and cross-axis reversal.
- `crates/nuxie-runtime/src/mechanical_port/source/layout/layout_component_style.rs:275` and `:308`: ordinary `layoutAlignmentType` simultaneously sets align-items and align-content to matching start/center/end. For rows the enum triplets 0–2,3–5,6–8 select cross start/center/end; for columns each triplet member selects cross start/center/end. Main alignment occupies the other dimension.
- `layout_enums.rs:53` enumerates exactly 0–11; invalid values panic at `:90`. Values 9/10/11 mean MAIN space-between, not distributed line alignment. They set cross items/content start/center/end respectively (`layout_component_style.rs:340`). Do not confuse these with CSS align-content:space-between.
- `layout_style_applier.rs:785` contains internal align-content space-between/space-around/stretch translations, but the ordinary flex-container property path above never requests them. No independently serialized align-content/align-items/align-self name was found in generated schema. Internal setter support alone is not file-level support. Grid/stack alignment paths are excluded from this task.
- `layout_participant.rs:268`: native child cross Fill sets align-self:stretch; other scale modes set auto, inheriting container alignment. Thus changing container line alignment also changes explicit CSS align-self:flex-start children unless lowering isolates their item alignment.

## Concrete hazards in current compiler

1. **Global reversal changes line membership.** `tools/html-to-riv/src/compiler.rs:13` always uses reversed native main flow, and `:467` reverses the entire order-sorted file stream for ordinary CSS row/column. The nowrap geometry compensation cannot extend directly to wrapping. Example widths 60,60,40 with available width100: forward collection gives [A], [B,C]; reversed gives [C,B], [A]. Reversing cross line order changes line sequence but cannot restore membership. Unequal line lengths and resize across thresholds are mandatory tests. This is a source-derived prediction awaiting native reproduction.
2. **Native alignment couples two independent CSS controls.** Existing start children are direct native participants; center/end children get perpendicular wrappers (`compiler.rs:481`). A parent content-center change would move direct fixed-size start children within each line too. Candidate: give every necessary child an item-alignment wrapper that stretches to the line cross size while aligning its authored child independently. Test fixed/auto cross dimensions, percentage containing blocks, min/max, intrinsic line contribution and safe overflow. Existing wrappers are not automatically qualified for line stretching.
3. **Baseline helper is a real flex item.** `baseline.rs:141` adds a zero-width measurement LayoutComponent to the original parent. In wrapping, it joins a particular line, may increase that line height or form an additional line at boundary/zero-space conditions, and no longer measures each line. Baseline participants currently share one global landmark; CSS sharing is per line. Last baseline targets parent bottom rather than each line bottom (`baseline.rs:147`). Do not silently allow either baseline mode in wrapping containers. This needs a separate line-local composition or a clear diagnostic.
4. **wrap-reverse changes cross start.** Current self-alignment handling collapses flex-start, start and self-start to one behavior (`compiler.rs:32–65`). These distinctions must remain computed identities: wrap-reverse flips flex-relative cross start/end while physical/logical start/end depend on writing mode/direction. Existing safe alignment auto margins are physical and require re-evaluation. Changing only flexWrapValue is insufficient.
5. **Intrinsic nested baseline summaries assume a single normal column.** `baseline.rs:35`, `:77`, `:91` derive y offsets by summing children or taking first order-modified child. Any wrapped column must cease using these summaries until line membership and propagated baseline rules are separately represented. This applies even when the wrapped box itself participates in an outer nowrap baseline group.
6. **Painting must be decoupled from layout before general wrap.** Compiler comments report pinned Chrome paints flex fragments in visual line order and native siblings in reverse file order. A correct geometry permutation cannot be presumed to preserve overlapping descendant pixels or line-to-line paint ordering. Preserve fixtures with overflow and transparent overlapping colors across both main and cross boundaries; compare actual pinned Chrome.

## Plausible ordinary-file leads, still unresolved

- Preserve order-sorted CSS participant stream for native line collection and investigate draw-order primitives independently. `draw_rules.rs:25` resolves ordinary DrawTarget by ID; `draw_target.rs:39` resolves a drawable, and placement 0/1 supports before/after. These could decouple layout sibling order from paint order without copying geometry or changing layout parents. Need to prove LayoutComponent drawable eligibility, nested subtree grouping, clone resolution, no cycles, and correct ordering when viewport changes line partitions. A fixed draw graph may still be insufficient for line-dependent Chrome paint order; this is a question, not a limitation claim.
- Alternative layout-only participants and separately ordered visible objects with ordinary constraints may preserve responsive geometry, but width/height transfer, percentage descendants, intrinsic dimensions, clipping and nested stacking need proof. Translation-only duplication is insufficient. Prefer investigating DrawRules first because it avoids duplicate layout trees.
- Fixed authored line wrappers are only valid where line membership is independently invariant under every allowed viewport. They cannot implement general wrapping by precomputing Chrome breakpoints or recompiling at resize. Avoid admitting a fixed-layout substitute as L06 support.
- Distributed align-content or stretch needs a genuine per-line arrangement. The native enum does not expose it independently; inserting authored spacer items affects line collection rather than distributing line boxes. A second outer container around native wrapped content might handle block start/center/end in limited profiles, but does not by itself distribute internal line gaps or stretch line cross sizes. Investigate without claiming impossibility.

3. Distinguish wrap with one collected line from nowrap: content alignment can matter in the former. Empty containers, zero-sized items, exact-fit thresholds and overflowing single items need controls.
4. Paint overflow across same-line and cross-line neighbors, nested transparent containers and changing line partition. Confirm draw-order candidate with pinned Chrome before reusing previous nowrap assumptions.
5. Reject baseline-in-wrap and wrapped-descendant baseline propagation until line-local metrics/anchors are proven. Preserve exact diagnostics in Rust/CLI/WASM/JS tests if public wrap is introduced before those combinations.

No L04/L06 status should change to qualified based on this report. Native wrap and coupled positional line alignment are candidates; independent item/line alignment, distributed lines, baseline groups and paint-order encoding remain unresolved.
