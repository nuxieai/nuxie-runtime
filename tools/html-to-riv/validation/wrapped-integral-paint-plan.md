# Source-certified integral paint fast path

Implementation correction: the historical34-owner table below contains an arithmetic error. Actual emitted total is17732, matching its stated formula. See wrapped-integral-review.md for measured results.

Read-only audit at compiler checkpoint `1b5322dc552d42c77143a67f859dacfba746d375`, 2026-09-12. No implementation, build, capture or new performance qualification was performed. The fixed-length optimization being developed concurrently has not been assumed in this argument. Counts below refer to the currently inspected 2,310-record rounded-box emitter.

The resource fixtures admit a useful source-based optimization: their parent stays at the origin, fixed integer slots pack from physical top/left, and visible children also align at physical top/left. For every fractional or integral viewport in the existing [0,16384]² domain, the viewport changes **which slots share a line**, but contributes no fractional translation to a box edge. An integral-paint certificate can therefore select ordinary ForegroundLayoutDrawable paint replicas without four rounding graphs per owner. Failed certification must select the current rounded path, preserving existing accepted input semantics and viewport domains.

## First certificate: sufficient conditions with no viewport-integer assumption

Bind these facts to the same immutable base and generated sizing records used by Candidate/Derived:

1. Reuse `wrapping_slots::inspect` and `wrapping_domains::resolve`. There is exactly one root layout parent at zero origin; root/parent/slot/visible transforms are identity; margins, insets, borders, padding and gaps are zero; no direction overrides, intrinsic sizing, baseline alignment, stretch/fill factors, animation, extra providers or feedback exist. Keep the original source ownership and explicit-minimum checks. The immutable fixed-size branch sets grow/shrink to zero (`layout_component.rs:3334–3360`); this is necessary, not an inference from integer authored widths alone.
2. Each slot and each visible used width/height is a finite **singleton integer** under the source-bound native f32 size resolver for the full original domain. Check `lower == upper` and the actual f32 value's integrality; integral endpoints of a non-singleton interval do not establish an integer lattice. Plain integer px sizes qualify, but also admit a percent/min/max expression if existing source provenance proves the same singleton result. Do not test CSS text, fixture name, particular owner count or sampled geometry. Native percentage resolution is `(coefficient * parent) * .01`; even `100%` of an integer parent must pass the actual resolver rather than a mathematical simplification.
3. First implementation: `reverse_main == false`, `reverse_cross == false`, `main_fraction == 0`, `line_fraction == 0`, requested visible cross alignment `a == 0` for every owner, and the slot's physical visible fractions are `[0,0]`. This exact scope covers the 1/3/8/34 resource recipes and both row and column variants. Equal visible/slot sizes are **not required** to prove integrality. Nonnegative integer visible extents suffice; zero extents need their explicit empty-path tests before enabling their optimization.
4. Bound every relevant integer sum/difference and transformed endpoint to a range where binary32 represents each integer exactly. A simple source-bound ceiling of 65,536 on cumulative slot extents and visible endpoints is sufficient and conservative relative to the 2²⁴ integer-exact limit; reuse tighter existing coordinate bounds where possible. Charge all intermediate sums, not just the final position. Retain the current finite graph/domain and separator proofs so multiplying an unused line maximum by zero cannot mask NaN/infinity. Retain the ordinary artboard clip and existing declared viewport domain.

The zero physical fraction is the important property. Native `LayoutAlignmentType` maps to FlexStart/FlexEnd, and Taffy's `compute_alignment_offset` uses free space when FlexStart is reversed. Merely testing the stored fraction equals zero while allowing reversals would be wrong. A later independently checked extension can require `main_fraction == (reverse_main ? 1 : 0)` and `line_fraction == (reverse_cross ? 1 : 0)`, plus requested alignment becoming physical zero, so reversed iteration still packs from physical zero. Qualify both positive and overflowing free-space branches before enabling that extension. It is not needed to optimize the resource recipes.

## Native arithmetic argument

The immutable layout disables Taffy's optional final rounding (`layout_component.rs:2073`), so native integrality must arise from the actual arithmetic. In the closed nonreversed physical-start case:

- Taffy's per-line main cursor starts at zero and adds fixed integer item sizes. The first and subsequent positional alignment offsets are zero because free-space distribution is physical start and the gap is zero. Container width may be any f32 value; it participates in line partition selection, not in these cursor sums.
- Each wrapping line's cross size is the maximum fixed integer slot cross extent. `align-content` is positional start, never stretch. The cross cursor starts at zero and adds integer line maxima. A dynamic partition therefore selects among sums of integers, without requiring enumeration of all partitions. Within-line physical-start slot offsets are zero.
- A slot's nonwrapping visible child has fixed integer extents and physical-start offsets zero. Even if its available cross size is fractional in a more general scope, physical-start contributes zero; the initial closed case already has singleton slot extents.
- The actual wrapping graph uses `p + h*f + L*(a-f) - v*a`. With physical `f=a=0`, the measured anchor is the integer slot top, the line-maximum factor is exactly zero and ComponentOrigin is zero. Finite line-maximum approximation errors therefore do not enter the visible position. Strength-one TranslationConstraint evaluates `old * 0 + target * 1`, retaining the integer target. Identity matrix operations and the zero local anchor must be bound, not assumed from trace labels.
- Adding the visible integer width/height to the integer leading coordinate is exact within the bounded integer range. All four raw paint edges are integral. Signed zero normalization is immaterial to coordinates.

This proof deliberately does **not** claim every carry/DistanceConstraint intermediate is integral. The current sizing proof may continue to carry conservative error bounds. The new certificate proves that this error-bearing value is multiplied by the actual emitted zero factor before reaching the visible owner. Changing alignment, copy factor, origin, operand or field defaults invalidates that reasoning. Layout ownership and the one-way slot → sizing → visible → paint dependency remain unchanged.

For an integer positive extent, Chrome's paint rounding is the identity and the one-pixel thin rule cannot change it. For exact zero extent, neither rounded nor ordinary rectangle should paint; that requires lifecycle/path/pixel tests. The certificate concerns native edges and the previously audited ordinary rectangular paint route. It does not transfer arbitrary CSS transforms, rounded corners, strokes or browser LayoutUnit semantics. Integer CSS/native fixtures still require Chrome correspondence evidence at wrap thresholds; native fraction-valued resize tests separately establish the noninteger viewport premise.

## Stronger optional path: retain original base paints

The resource fixtures also satisfy `visible_width <= slot_width` and `visible_height <= slot_height` (equality in all four fixtures), with physical-start placement. This supplies a separate nonoverlap proposition: within a line, painted visible rectangles fit in distinct sequential main-axis slots; across lines, they fit within each line's cross-extent band. Oversized slots may overflow the parent, but wrapping puts their following line below/after the integer line maximum, so it does not create positive-area overlap. The artboard clip only removes coverage. Alpha is allowed because painted interiors are disjoint. Shared integer edges need pixel verification for coverage/antialias behavior.

Under an independently bound nonoverlap certificate, restoring original solid base paints and omitting the whole paint replica/gate/order suffix is plausible. Natural base traversal order then cannot alter overlapping color because positive-area overlaps are excluded. Keep the sizing graph in the first implementation: the paint certificate does not authorize deleting sizing proof or its visible constraints. The proposed total becomes `64N − 26`: 38, 166, 486 and 2,150 records for 1/3/8/34 owners. This stronger path must fall back to ordered foreground replicas when a visible dimension exceeds its slot or when any condition is unknown. Equal dimensions alone are insufficient if viewport-dependent offsets, transforms, margins or unbound positioning survive.

Do the ordered foreground path first unless the nonoverlap proof and draw behavior can be implemented and validated together. Do not silently infer paint order irrelevance from the current resource captures. A future redundant-sizing optimization is separate: it must prove native visible geometry already equals the requested landing, revise sizing ownership/binders and preserve all lifecycle behavior.
