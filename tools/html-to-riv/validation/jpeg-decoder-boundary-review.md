# Immutable JPEG decoder boundary

**No ordinary Rive file property was found that controls JPEG decoder selection, chroma reconstruction or decoded color space in the pinned Mac path.** The observed 1×17 4:2:0 mismatch therefore remains a target limitation with no identified ordinary-image repair that preserves the original encoded bytes. This is a bounded source assessment, not proof that every possible Rive composition or every 4:2:0 image must fail.

The [receipt](../output/jpeg-decoder-boundary-r1/receipt.json) verifies 13 relevant source files against immutable baseline `6c7ac16617835b5f581784ff08a9e779bb52faf3` and the prior frozen source snapshots. It also rechecks all 48 retained 1×17 frames: geometry passes throughout; the PNG, 4:4:4 baseline and 4:2:2 baseline/progressive controls pass pixels; both 4:2:0 files fail across their eight original/clone frames. No new render was run.

## Where decoding happens

`FileAssetContents.bytes` (212) reaches [`FileAssetImporter::resolve`](../../../crates/nuxie-runtime/src/mechanical_port/source/importers/file_asset_importer.rs). With no successful host loader, it calls the asset decoder. [`ImageAsset::decode`](../../../crates/nuxie-runtime/src/mechanical_port/source/assets/image_asset.rs:53) passes **only encoded bytes** into `Factory::decode_image`; authored dimensions, sampler state, fit and file metadata do not become decoder arguments.

The baseline recording factory preserves those bytes in `decodeImage`. Stream replay calls the native factory, whose installed [`MechanicalBitmapDecoder`](../../../crates/nuxie-renderer/src/native_metal/mechanical_render_context.rs:140) invokes `nuxie_image_codec::decode_image_rgba`. The Mac JPEG implementation calls [`decode_macos_image_rgba`](../../../crates/nuxie-image-codec/src/lib.rs:638): `CGImageSourceCreateWithData` and `CGImageSourceCreateImageAtIndex(..., 0, NULL)` receive null options, followed by a full-size draw into a fixed eight-bit DeviceRGB bitmap. This yields RGBA before image texture upload and any scene draw.

The codec source SHA-256 is `187aa3c58d0ad3fa772c3f8ab30a3b0dcb012ecf6604e5f4b4c083cc90242d69`. The receipt contains hashes and frozen copies for the importer, asset, image, generated fields, recording/stream and native decoder paths as well. The platform decoder's internal chroma algorithm is not visible in these sources; the observations support a platform JPEG reconstruction difference without establishing Apple's exact algorithm.

## Existing controls and their limits

| Ordinary file control | Actual effect and relevance |
| --- | --- |
| ImageAsset dimensions 207/208; asset identity and metadata | Dimensions are used for layout/fallback metadata; successful decode supplies actual image dimensions. Asset names/extensions do not change signature-based format dispatch. Identity/CDN/signature fields expose no JPEG decoding option. |
| ImageAsset sampler 1073–1075; Image overrides 1076–1078 | Select bilinear/nearest and clamp/repeat/mirror when drawing the already decoded RGBA texture. They do not reach ImageIO or independently select Y/Cb/Cr reconstruction. |
| Image fit 974, alignment 975/976, origin 380/381, transform, mesh and owner clip | Scale, position, sample or clip existing texture pixels. They provide no alternative decoding path. |
| Drawable opacity/blend and ordinary color overlays | Combine existing RGBA colors after decode. A constant correction cannot generally repair content-dependent spatial chroma errors; an asset-specific overlay would require a separately justified reconstruction strategy and its own correctness evidence. |

The separation is explicit in [`Image::draw_occurrence`](../../../crates/nuxie-runtime/src/mechanical_port/source/shapes/image.rs:96) and [`Image::image_sampler`](../../../crates/nuxie-runtime/src/mechanical_port/source/shapes/image.rs:558). JPEG chroma reconstruction precedes RGB conversion; resampling the resulting RGB texture acts on all color channels and cannot simply select a different chroma-only interpolation rule.

No plausible ordinary decoder-setting candidate was found. This review adds no rendering experiments or alternative host decoding policy.

## Observed scope

The failing retained frames use intrinsic and computed size 1×17, scale `(1,1)`, and integer translation `(20,20)`. Their image-region mean RGB difference is `9.686274509803921`, with maximum channel difference **29**. At authored row 3, Chrome RGB is `(238,52,63)` and native is `(210,66,66)`; at row 4 the difference reverses direction: `(125,103,79)` versus `(153,90,73)`. The difference is spatial, not a uniform tint or opacity offset. The receipt binds the original asset/scene bytes, recording stream and complete retained PNGs and recomputes those values.

The later [width and horizontal controls](../output/jpeg-decoder-boundary-r1/boundary-supplement.json) strengthen the context boundary: vertical-pattern widths 1–4 at height17 fail 32/32 4:2:0 frames, while widths5/6 pass16/16. The horizontal-pattern corpus passes geometry88/88 and pixels48/88: widths3/4 expose additional 4:2:2/4:2:0 color differences. The 4×17 4:2:2 uniform-horizontal control passes, while the same dimensions with horizontal color changes fail. Context alone does not imply every image fails; a passing constant-chroma control does not qualify the whole context.

The primary [libjpeg-turbo3.1.0 upsampler](https://github.com/libjpeg-turbo/libjpeg-turbo/blob/3.1.0/src/jdsample.c#L443) selects its enhanced interpolation only when `do_fancy && downsampled_width > 2`, for both 2h1v and 2h2v paths. The exact source is frozen in the supplement. This is a plausible explanation consistent with the observed small-chroma-plane boundary, **not identification of Chrome153's exact decoder release or proof of ImageIO's internal algorithm**.

The former tiny-image exception is **invalidated**. The public `single-chroma-2x1-420-baseline` source passes geometry but fails all eight original/clone pixel frames: image-region and interior mean RGB error are both **7.5**, exceeding the unchanged limit of 6. Chrome's two pixels are `(122,106,81)` and `(135,119,94)`; native produces `(122,106,80)` and `(107,133,96)`. The [revised review receipt](../output/jpeg-decoder-boundary-r1/revised-gate-review.json) independently verifies those retained PNG pixels, the exact authored asset bytes in every recorded decode operation, and request/RIV/map/HTML/stream/geometry hashes. One logical chroma sample therefore does not establish equivalent reconstruction. Encoded padding may contribute, but this source audit cannot establish ImageIO's closed implementation. The [old gate receipt](../output/jpeg-decoder-boundary-r1/gate-review.json) and [old review](../output/jpeg-decoder-boundary-r1/invalidated-exception-review.md) remain unchanged as evidence of the invalidated exception candidate.

The revised compiler gate diagnoses **all admitted 4:2:2 and 4:2:0 sampling patterns with width≤4**, including tiny inputs and 4:2:2 widths1–2. These are conservatively unqualified contexts, not a claim that every file in each context fails. The reviewed `assets.rs` SHA-256 is `af8e9fc9cc8795c2c434b25c705b6c67f339f1f83d14014248fd0125a0fb8c0e`; its exact predicate is `[0x21 | 0x22, 0x11, 0x11] => width <= 4`. It follows strict entropy validation, keeps original bytes, and leaves 4:4:4 unchanged. The strict validator remains `a637966ee9fedd8e5689bae1d655248e78dfffe4e8605cc2cf2e82eda78ca8f9`. The context diagnostic precedes full portable pixel decoding, so an unsupported context can be reported before a later decoder-only defect; no such input is accepted by that shortcut. Tiny or content-specific exceptions remain unresolved and have no admission claim. This source-and-retained-evidence check does not replace the final public API/build qualification.

These results do not establish that every image in a rejected context fails, that all other contexts are universally identical, or that another operating system has the same behavior. The non-Mac codec path already differs, but choosing it here would require a host/build/runtime change rather than an ordinary file property. Custom asset loaders, replacing the render image, changing decoder options, and transcoding or replacing authored pixels remain outside this immutable, original-byte-preserving scope. Until a qualified file composition is demonstrated, this case should remain explicitly flagged as unsupported rather than reported as Chrome-equivalent.
