# Upstream parity workflow

This is the reusable operating model for ports whose authoritative
implementation already exists. It applies to native Metal, a future WebGPU or
Vulkan adapter, and unfinished parity work in the main runtime. Backend guides
may add stricter requirements, but they should not redefine this workflow.

The objective is not merely to produce Rust that looks like the upstream
source. A completed port preserves observable output, state transitions,
ownership, failure behavior, platform artifacts, and relevant performance and
size characteristics. Upstream is the default authority; every intentional
departure is named and evidenced.

## The unit of work

Partition work by the smallest independently testable upstream behavior, not
by an arbitrary number of files. A useful slice has all of the following:

- an exact upstream revision and source range;
- a named Rust owner and exclusive file ownership while work is parallel;
- an input and an observable output or state transition;
- an oracle or checked-in fixture;
- a bounded integration seam;
- a clear promotion condition.

Generated sources, lifecycle owners, and platform build products often cross
file boundaries. Keep those closures together even when the mechanical source
translation could be split more finely. Shared seams belong to the integrator;
leaf implementers should not independently reshape them.

## Evidence before translation

Record enough provenance to reproduce the authority:

1. upstream repository and exact commit;
2. complete source and header closure;
3. generator versions, inputs, command, and output hashes;
4. compiler flags, SDK, deployment target, and target triple;
5. the reference runner or fixture and its adapter identity;
6. state-bearing owners and their construction, reuse, completion, and drop
   transitions.

Never call generated bytes deterministic merely because a random seed was
fixed. If upstream emission order depends on identity hashing, retain a
byte-exact captured emission with provenance and separately test normalized
semantic equivalence.

## Execution loop

Use this loop for every slice:

1. **Pin and inventory.** Verify the checkout is at the recorded revision and
   classify every source and state-bearing owner in scope.
2. **Write the behavioral test.** Start with a public-interface differential,
   state-transition test, or exact generated fixture. Observe it fail for the
   missing behavior.
3. **Translate the smallest closure.** Preserve upstream ordering, defaults,
   enum values, resource timing, and failure paths. Do not mix cleanup or a
   speculative cross-platform abstraction into the translation.
4. **Run focused validation.** A test command is evidence only when the
   expected nonzero test count actually ran. A standalone harness is useful
   during conversion but provisional until the module is compiled and tested
   through its real crate.
5. **Review against upstream.** Compare the complete source ranges side by
   side. Review lifetime and unsafe interop separately from output parity.
6. **Integrate through the real seam.** Replace test-only wiring with the
   production construction and ownership path, then rerun focused tests.
7. **Build every affected platform target.** Inspect the resulting artifact,
   not only Cargo's exit code: target metadata, SDK/deployment target, exported
   functions, runtime loading, and architecture must be correct.
8. **Run the applicable oracle ladder.** Advance from static contracts to
   intermediate data, lifecycle, pixels/results, hostile inputs, performance,
   and product closure. Do not skip lower rungs because a broad corpus passes.
9. **Measure the rooted artifact.** Binary-size or dependency-removal claims
   use the final consumed Mach-O, ELF, library, or package built from identical
   roots and toolchains. Source deletion and `.rlib` estimates are not proof.
10. **Promote and checkpoint.** Update manifests, ownership records, issue
    tracker, and the merge checkpoint only after the evidence exists.

### Live GPU diagnosis loop

GPU slices need a shorter inner loop inside steps 4–8. A final black or
corrupted frame does not identify whether the defect is resource preparation,
binding, shader interpretation, or rasterization. Use this order:

1. Enable the platform API validation layer and shader validation on every
   live slice. Treat a validation-clean command buffer as a prerequisite, not
   as pixel-parity evidence.
2. Read back each newly introduced intermediate resource before debugging the
   final pass. This separates upload/prepass defects from draw-pass defects.
3. Bind and test upstream constants by name. Vertex counts, sampler slots,
   instance offsets, and sentinel values are behavioral contracts even when a
   small fixture appears to tolerate another value.
4. Exercise inactive-feature sentinels used by the fully featured shader. For
   example, an unclipped draw may require upstream's explicit wide-open clip
   matrix rather than zero-filled auxiliary data.
5. Change one variable to prove causality, then restore it. Reproducing an
   artifact with a zero base instance is stronger evidence than repairing it
   through an unrelated layout change.
6. Compare against the same-backend pinned upstream oracle first. Keep a
   cross-backend oracle in a separate manifest so its larger rasterization
   tolerance can never weaken the primary parity gate.
7. Require exact bytes and occupancy when stable. Permit a small numeric delta
   only when the pinned same-backend oracle demonstrates hardware rounding,
   and record the bound next to the fixture.

This loop is reusable for Metal, WebGPU, Vulkan, and the main runtime wherever
an intermediate state can be captured before the final observable result.

Root the highest public seam named by the claim. A headless renderer executable
can prove pixel output and forbidden-dependency absence while dead stripping
the platform presentation adapter entirely. When the claimed slice includes a
product surface, the measured executable must also acquire the caller-owned
target and execute presentation through that public boundary.

For Objective-C lifetime evidence, put the operation under an explicit
autorelease pool and inspect weak references only after that pool drains. A
Rust `Retained<T>` owner can be gone while an autoreleased native reference is
still alive, so checking immediately after Rust `drop` does not prove native
deallocation. Conversely, a layer may recycle drawable slots without
deallocating the drawable object; test the product-visible lifecycle event
rather than assuming pointer death is the contract.

## What parity means

For each slice, explicitly consider these dimensions:

| Dimension | Typical evidence |
|---|---|
| Output | Byte-exact fixture, differential result, pixel comparison |
| Decisions | Exhaustive enum/flag table, pipeline or dispatch-key oracle |
| Lifecycle | State-transition trace for create, reuse, submit, complete, abandon, resize, and drop |
| Ownership | Retention/drop tests and documented unsafe invariants |
| Failures | Typed error and fail-closed tests, including worker panic or device failure |
| Platform artifact | Target/SDK metadata, function inventory, runtime load |
| Physical work | Pass, draw, upload, allocation, and submission counts |
| Distribution | Final artifact size and forbidden-dependency reachability |

Output parity alone is insufficient for stateful systems. A buffer that rotates
on `unmap` instead of submission can render the same small fixture and still be
wrong. A background worker that reproduces shader bytes but can strand a
blocking waiter after a panic is likewise incomplete.

Names are not ownership proof. This Metal port contains both a user-facing
`RiveRenderBuffer` ring and separate RenderContext upload/uniform rings; they
share vocabulary but have different source ranges, lifecycle transitions, and
integration seams. Before extending a plausible existing type, trace its
constructor and submission owner back to upstream. Port distinct owners as
distinct modules until evidence demonstrates a real common abstraction.

## Adaptations and divergences

Rust safety and library APIs sometimes require a different shape. The change
is acceptable only when the preserved upstream invariant is stated beside the
implementation, the manifest records the adaptation, and a focused test proves
it. Never silently improve upstream during a mechanical port.

If pinned upstream behavior is demonstrably incorrect for the target API, use
an explicit divergence with exact evidence. The Metal ASTC pixel-format table,
for example, crosses a reserved enum value that upstream arithmetic does not;
the Rust table is justified by the platform enum and an exhaustive test. This
is the exception pattern, not permission to redesign nearby code.

## Parallelism and model assignment

### File-first mechanical translation phase

When a complete pinned upstream subsystem is already present, source files —
not product features — drive the translation queue. This follows the process
described in [Bun's Rust rewrite](https://bun.com/blog/bun-in-rust): prepare a
translation guide and lifetime ledger, mechanically translate the complete
source inventory, review the translations in separate contexts, then use
compiler errors and the language-independent test suite as later work queues.

For C++ backends, one **ownership unit** is the smallest independently owned
class closure. It may contain an interface header plus a platform header and
implementation file because C++ splits one owner across those files. Every
upstream file remains individually accounted for in the source manifest even
when several files form one ownership unit.

The phases are deliberately separate:

1. **Preparation:** pin the source inventory; write the C++→Rust convention
   table; record every state-bearing field in the lifetime ledger; partition
   every source into a dependency-ordered ownership unit with one exclusive
   Rust target set. The manifest records the base snapshot, worker claim,
   reviewer/fixer roles, and state of every unit before translation begins.
2. **Three-unit trial:** one Luna extra-high implementer translates each unit;
   two Sol high reviewers independently compare source and translation; one
   fixer applies accepted findings. Revise the workflow, not just the trial
   code, when a repeated failure pattern appears.
3. **Bulk translation:** only after the lifetime ledger covers the entire
   subsystem, translate every remaining source unit mechanically.
   Translation workers do not run Cargo, Git, generators, broad formatting, or
   tests and do not wire shared modules. They edit only their assigned files.
4. **Compiler work queue:** the integrator wires the translated modules, runs
   `cargo check` once per crate, saves and groups diagnostics by Rust file, and
   assigns non-overlapping fixes. Stubs, `todo!`, swallowed errors, and no-op
   implementations are rejected.
5. **Behavior work queue:** after compilation, existing language-independent
   oracles, structural harnesses, and product roots validate the translated
   subsystem. Feature fixtures are acceptance evidence; they do not dictate
   the source module structure.
6. **Refactoring:** idiomatic cleanup and shared-HAL extraction wait until the
   complete concrete backend is at parity.

The three-unit trial is integrated into a private module and must compile and
run focused structural tests before the workflow is approved for bulk use.
Later bulk translations may remain unwired until the compiler-queue phase, but
the trial is specifically where imports, trait shapes, native-handle types,
and `Send`/`Sync` assumptions are proven.

The implementer never reviews its own output. Reviewers receive the upstream
source set, the Rust diff, the porting guide, and the lifetime rows, but not the
implementer's reasoning. One reviewer attacks behavioral/source
correspondence; the other attacks ownership, unsafe interop, and repository
standards. These two mechanical-translation reviews establish source fidelity;
they are distinct from the single optional, time-boxed behavioral review
allowed by `PORTING.md` after the implementation-independent tests have run.

Parallelize independent leaf closures, not shared architecture:

- keep two or three implementation lanes active when independent closures
  exist;
- give each lane exclusive source and Rust file ownership;
- reserve manifests, module wiring, public interfaces, and shared ownership
  seams for one integrator;
- use an isolated, clean tool environment for additional CLI workers so local
  plugins and configuration cannot pollute their output;
- stop a lane when it discovers an unplanned shared seam and return the
  decision to the integrator.

For this repository, Luna at extra-high effort is the mechanical converter for
bounded, source-corresponding leaves. Sol at high effort partitions work,
designs or changes ownership seams, integrates, and reviews all parity claims.
Luna never reviews its own or another worker's translation. Using one stable
effort level per role has produced less rework than varying intelligence to
save marginal conversion cost.

## Status and progress

Use the ledger states literally:

- `pending`: inventoried, with no integrated Rust owner;
- `in-progress`: some real behavior exists, but the source or ownership
  contract is incomplete;
- `ported`: the complete scoped owner is integrated and focused real-crate
  evidence passes;
- `verified`: the issue-level parity oracle and required platform/product gates
  have produced checked-in evidence.

Progress is visible as source and ownership rows advance, not as lines of Rust
written. At each merge checkpoint report:

- rows by status and which ownership contracts advanced;
- focused tests with actual executed counts;
- target/platform matrix results;
- exact differential corpus results;
- review findings and resulting rework;
- final artifact size/dependency deltas when that gate is in scope.

If those measures do not advance, the campaign is spinning even if conversion
volume is high.

## Applying the workflow elsewhere

- **Metal:** `METAL_PORTING.md` supplies the Metal ownership rules, artifact
  matrix, oracle ladder, and slim-Apple closure.
- **WebGPU and Vulkan:** create backend-specific guides and ledgers that apply
  this workflow. Port the concrete implementation first. Extract a shared HAL
  only after two concrete adapters demonstrate the same variance behind a
  small interface.
- **Main runtime parity:** substitute serialized/intermediate differentials and
  ownership/state traces for GPU artifact checks. Keep the same pin,
  correspondence, nonzero-test, divergence, review, and promotion rules.

The desired architecture follows from completed concrete ports: a small,
stable interface over deep backend modules. It should not be guessed before
the second adapter demonstrates which behavior is genuinely common.
